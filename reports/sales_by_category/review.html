1. Things to check before approving

Found by our own code, not by the AI. Each one is a way the report could be wrong even though the test months match.

  • Date filter: OrderDate is compared with '<= @end_date' (or BETWEEN). OrderDate holds a date AND a time, so rows with a time during the last day are left out. Safer: OrderDate < DATEADD(day, 1, @end_date).
Good to know about the joins (4)
  • Join Sales.SalesOrderHeader -> Sales.SalesOrderDetail - MULTIPLIES ROWS: one Sales.SalesOrderHeader row can match many Sales.SalesOrderDetail rows, so values from Sales.SalesOrderHeader (and tables joined before it) repeat. Do not sum them after this join.
  • Join Sales.SalesOrderHeader -> Sales.SalesOrderDetail - MAY DROP ROWS: Sales.SalesOrderHeader rows with no matching Sales.SalesOrderDetail row are left out.
  • Sales.SalesOrderDetail is joined straight to Production.Product (SalesOrderDetail.ProductID = Product.ProductID). The database does not declare this link. It matches on the primary key of Production.Product, so it cannot duplicate rows, but confirm it means what the SOP intends.
  • Join Production.Product -> Production.ProductSubcategory - MAY DROP ROWS: Production.Product rows where ProductSubcategoryID is empty are left out.

2. The written procedure and the SQL

Written procedure (SOP)
Monthly sales by product category

1. Take every sales order whose order date is within the report period
   (from the start date to the end date, both included).
2. Look at each line of those orders and find the category of the
   product on that line.
3. For each product category, add up the quantity ordered and the
   line total.
4. Show three columns: Category (the category name), Units, Sales.
   Round Sales to 2 decimal places.
5. Sort by Category name, A to Z.
SQL
-- Report:     Monthly sales by product category
-- Status:     PASSED - awaiting human review
-- Tested on:  {'start_date': '2025-03-01', 'end_date': '2025-03-31'} and held-out {'start_date': '2025-04-01', 'end_date': '2025-04-30'}
-- Written by: gemini-3.5-flash on 2026-10-06, attempt 1 of 5
-- Parameters: @start_date date, @end_date date
-- Tables:     Production.Product, Production.ProductCategory, Production.ProductSubcategory, Sales.SalesOrderDetail, Sales.SalesOrderHeader, Sales.SpecialOfferProduct
SELECT pc.Name AS [Category], SUM(sod.OrderQty) AS [Units], CAST(SUM(sod.LineTotal) AS DECIMAL(18,2)) AS [Sales]
FROM Sales.SalesOrderHeader AS soh
INNER JOIN Sales.SalesOrderDetail AS sod
    ON soh.SalesOrderID = sod.SalesOrderID
INNER JOIN Production.Product AS p
    ON sod.ProductID = p.ProductID
INNER JOIN Production.ProductSubcategory AS ps
    ON p.ProductSubcategoryID = ps.ProductSubcategoryID
INNER JOIN Production.ProductCategory AS pc
    ON ps.ProductCategoryID = pc.ProductCategoryID
WHERE soh.OrderDate >= @start_date AND soh.OrderDate <= @end_date
GROUP BY pc.Name
ORDER BY pc.Name ASC;

The query starts from the SalesOrderHeader table, filtering orders within the specified date range. It then joins SalesOrderDetail to get the order details (quantity and line totals), Product to find the specific products, and ProductSubcategory and ProductCategory to get the category names. Finally, it aggregates the quantities and line totals (rounded to 2 decimal places using CAST to DECIMAL(18,2)) grouped by the category name, sorting the final report by category name from A to Z.

SELECT pc.Name AS [Category], SUM(sod.OrderQty) AS [Units], CAST(SUM(sod.LineTotal) AS DECIMAL(18,2)) AS [Sales]
FROM Sales.SalesOrderHeader AS soh
INNER JOIN Sales.SalesOrderDetail AS sod
    ON soh.SalesOrderID = sod.SalesOrderID
INNER JOIN Production.Product AS p
    ON sod.ProductID = p.ProductID
INNER JOIN Production.ProductSubcategory AS ps
    ON p.ProductSubcategoryID = ps.ProductSubcategoryID
INNER JOIN Production.ProductCategory AS pc
    ON ps.ProductCategoryID = pc.ProductCategoryID
WHERE soh.OrderDate >= @start_date AND soh.OrderDate <= @end_date
GROUP BY pc.Name
ORDER BY pc.Name ASC;
